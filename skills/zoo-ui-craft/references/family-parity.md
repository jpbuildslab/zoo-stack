# Family Parity

Start with the nearest accepted sibling. Identify what makes it recognizable as part of the same
family, such as first-read hierarchy, scan path, geometry, density, typography, action priority, and
status treatment. Match that presentation where it serves the target. Preserve geometry specific to
the task, such as the reading width of a document or the scan density of a queue.

Use the target's own labels, calculations, lifecycle, eligibility, permissions, data, and commands.
Check equivalent lifecycle points for meaningful actions and context. If the family supports
continuing from a result, verify how the target supports that next step and whether a visible
blocker is needed. Base any omission or change on the target's task and contract.

Preserve stable context while the active task changes where the family calls for it. At narrower
widths, adapt the layout and controls while keeping the same information, action eligibility, work
in progress, and recovery options. Keep focus and reading order useful when regions move or
collapse.

Reuse existing components where their responsibilities fit. Extract shared code when real consumers
demonstrate a stable shared responsibility. Bring an accepted improvement to earlier siblings when
the request covers them.
