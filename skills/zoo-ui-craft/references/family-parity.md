# Family Parity

Start with the nearest accepted sibling. Identify what makes it recognizable as part of the same
family, such as first-read hierarchy, scan path, geometry, density, typography, action priority, and
status treatment. Match that presentation where it serves the target. Preserve geometry specific to
the task, such as the reading width of a document or the scan density of a queue.

Use the target's own labels, calculations, lifecycle, eligibility, permissions, data, and commands.
When a workflow gains working surfaces or decision inputs, map what users need to recognize,
decide, and do on each surface. Group and name information for those jobs before mapping fields
to components. For example, an approval can show who approved and when while the service retains
the revision needed for a stale-write check. Keep required evidence accessible in the form and
place the product expects.

Establish which context stays visible, where routine and conditional controls belong, and what
scrolls at the widths where the arrangement changes. Preserve decision inputs, action eligibility,
work in progress, and recovery when regions move or collapse. For an external reference, identify
the task and state shown, the decision to borrow, what differs here, and the interaction or render
that can test that choice.

Reuse existing components where their responsibilities fit. Extract shared code when real consumers
demonstrate a stable shared responsibility. Give meaningful variants explicit names when combinations
of flags make them hard to recognize or allow conflicting states. Bring an accepted improvement to
earlier siblings when the request covers them.
