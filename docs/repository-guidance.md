# Connect Zoo to a repository

The repository owns product truth. Zoo methods describe the questions to resolve and evidence to
seek; they should not carry a second copy of the product handbook.

## A small interface through existing documents

Start from the assigned repository's instructions. Link the existing owners of these decisions:

| Decision | What the repository should expose |
| --- | --- |
| Current scope | Instructions, current plans, source ownership and allowed effects |
| API behavior | Exposure, actor/resource authority, schemas, data-access conventions and exceptions |
| UI behavior | Controller, role/capability states, action/recovery contracts and destinations |
| Presentation | Live tokens/components, accepted family examples and current owner direction |
| Verification | Commands, substitutions, runtime resources and decisive assertions |
| Acceptance | Tested behavior, accepted visual decisions and unresolved questions |

Use a task map when these owners are spread across documents. Read the relevant section and source,
not every file on every task. Links should work within that repository. No mandatory profile filename,
schema, generated state store or model configuration is introduced by Zoo.

If portable Zoo and a repository workflow overlap, run one process. The general entrypoint chooses
the method; the repository workflow and craft definitions settle product decisions. Do not compose
overlapping legacy and replacement methods merely because both are installed.

## UI reference quality

A useful reference identifies the operator/task, production component and token sources, relevant
synthetic states, responsive behavior, interaction checks and the exact dimension accepted by its
owner. Existing components and experimental samples are evidence to inspect, not automatic design
approval. Current owner direction can request a new candidate.

Use production presentation components with synthetic inputs where practical. Keep mocked services
and omitted behavior visible in the example's scope. Avoid copying a controller into a gallery or
creating a second design system that drifts from the application.

Reference loading should support a concrete decision: hierarchy, action priority, density, state,
copy, focus or responsive transformation. Record accepted improvements in existing product docs.
Do not make a universal layout from unrelated workflows that happen to look similar.

## Maintain the boundary

Keep generic skill source in one maintained package and record the exact version installed in the
product. Put product changes in its definitions. Update a package at a task boundary with the prior
version recoverable and a fresh loading check. Preserve another writer's local adaptations.

If product experience suggests a generic improvement, describe it with synthetic inputs and its
observable failure. Do not export private code, customer records, screenshots, paths or raw chat
history merely to justify a public instruction change.
